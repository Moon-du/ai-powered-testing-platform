# P0 Security Baseline

This checklist turns the master PRD's security and AI guardrails into implementation and release gates. Defaults apply until an owner records a replacement decision.

## Scope and defaults

- P0 is an engineering-assistance system, not a formal QMS, validated record system, or autonomous test authority.
- The initial deployment may serve one enterprise, but storage and authorization remain tenant-aware. Product knowledge may be reused across projects only inside the same tenant; cross-tenant sharing is forbidden.
- Local development and automated tests use `FakeLLMGateway`, deterministic fixtures, synthetic requirements, and demo knowledge only. Proprietary documents and external AI endpoints are outside the development boundary.
- AI output remains a draft until an authorized human approves it. Only approved, non-stale assets may be exported.

## P0 Now

### Build checklist

- [ ] Put `tenant_id` on every tenant-owned business row, vector row, object record, job, and audit event. Put `project_id` on every project-owned resource.
- [ ] Add explicit knowledge visibility (`TENANT`, `PROJECT`, or `PLATFORM`); default to `TENANT`. Do not allow `PLATFORM` publication in P0 without a separate administrator control.
- [ ] Centralize authorization in the service layer and fail closed. Enforce it for list/detail, mutation, review, AI-run polling, traceability, knowledge references, upload/download, and export; UI state is never an authorization boundary.
- [ ] Persist project membership and role binding. `PROJECT_MEMBER` may generate/edit, `PROJECT_REVIEWER` may approve, and only `PRODUCT_ADMIN` may maintain or publish product knowledge.
- [ ] Gate the development identity adapter behind an explicit development setting. Refuse startup with it in any non-development environment.
- [ ] Keep browser access tokens in memory, never local storage. Keep production authentication behind an OIDC/JWT adapter.
- [ ] Treat uploaded or retrieved text as untrusted evidence, never as system instructions. Context construction must apply tenant/project filters before retrieval.
- [ ] Give agents no direct database, filesystem, network, URL-fetch, or persistence capability. Accept only typed output through schema and domain validators.
- [ ] Reject every knowledge reference whose tenant, project, pack/version, type, or applicability does not match the AI run.
- [ ] Record AI lineage: actor, tenant/project, task, provider/model identifier, prompt version, validator/policy version, requirement/pack/context revisions, retrieved IDs, input hash, output hash, timestamps, duration, and result status.
- [ ] Disable raw prompt and raw provider-response persistence by default. Persist the validated structured result and hashes needed for replay/audit.
- [ ] Emit structured logs only. Never log document bodies, retrieved chunks, prompts, generated content, bearer tokens, cookies, secrets, signed URLs, or full exception payloads containing user data.
- [ ] Scope an idempotency key by tenant, actor, endpoint, and request-body hash. A repeated delivery must return the original run/result rather than create another asset.
- [ ] Make Celery persistence atomic and retry-safe. Default to three retries with exponential backoff and jitter; add timeout, cancellation, dead-letter handling, and reconciliation for stuck `QUEUED`/`RUNNING` jobs.
- [ ] Keep Redis coordination-only; PostgreSQL/object storage remain the source of truth. A worker crash must not leave a partially active asset.
- [ ] Use opaque object keys generated by the server. Buckets are private; user filenames never become filesystem paths or authorization keys.
- [ ] Export only approved, non-stale records. Neutralize spreadsheet formulas for any cell beginning with `=`, `+`, `-`, `@`, tab, carriage return, or newline.

### Acceptance gate

- [ ] A generated cross-scope test matrix proves zero successful cross-tenant or cross-project read, list, write, review, poll, download, export, and knowledge-reference requests, including guessed UUIDs.
- [ ] Role tests prove a member cannot approve and a non-admin cannot maintain/publish product knowledge.
- [ ] A prompt-injection corpus cannot change system policy, cause tool/network access, expose another scope, or create an out-of-scope reference; all invalid references are rejected.
- [ ] Ambiguous expected behavior always produces `CLARIFICATION_REQUIRED`/`UNDEFINED`, never an invented expected result.
- [ ] Worker crash, timeout, retry, and duplicate-delivery tests produce no duplicate asset, no partial active version, and a deterministic terminal/recoverable state.
- [ ] Canary secrets placed in test input do not appear in logs, traces, metrics, errors, or stored raw-output fields.
- [ ] Export tests prove stale/unapproved data is blocked and formula-like cells are neutralized without losing displayed text.

## Before real data

### Build checklist

- [ ] Approve a data classification and handling policy covering proprietary data, personal information, sensitive personal information, credentials, source code, regulated records, residency, cross-border transfer, retention, deletion, and incident notification.
- [ ] Default upload allowlist to DOCX and plain text for the first adapter, with a 25 MB per-file limit. Validate extension, MIME type, and magic bytes; compute a content hash.
- [ ] Scan uploads for malware and active content. Reject encrypted files, macros, embedded executables/objects, external relationships, decompression bombs, and unsupported parser features.
- [ ] Run parsers in a low-privilege sandbox with no network, read-only packaged dependencies, isolated temporary storage, and CPU, memory, file-count, and time limits.
- [ ] Define deletion as a cascade across PostgreSQL, pgvector, object storage, parser temporaries, caches, queued jobs, and derived AI assets. Record the deletion audit event without retaining deleted content.
- [ ] Use these provisional retention defaults: parser temporary files 24 hours, application logs 30 days, security/audit events 365 days, optional privileged AI raw payloads 7 days, and backups 35 days.
- [ ] Keep object storage private and encrypted. Issue user-bound download URLs for at most five minutes and recheck authorization before issuance.
- [ ] Approve each LLM, embedding, and OCR provider for data type, endpoint region, retention, subprocessors, breach notification, and deletion. Contractually disable training on customer data; provider retention defaults to zero and must not exceed seven days.
- [ ] Minimize and, where required, redact context before provider calls. Permit egress only to approved endpoints. Do not automatically fail over to a provider with a different data boundary.
- [ ] Store provider keys only in an approved secret manager; never in source, images, fixtures, client code, logs, or database content fields.

### Acceptance gate

- [ ] Malicious, spoofed-type, oversized, encrypted, active-content, external-reference, path-traversal, and decompression-bomb fixtures are rejected safely.
- [ ] Parser tests prove no outbound network access and no read/write access outside the assigned input/temp paths.
- [ ] A deletion test proves online copies and derived embeddings are inaccessible within 24 hours; backup copies expire within the approved backup window.
- [ ] Provider integration evidence confirms approved region, training disabled, retention setting, TLS, and absence of unapproved fallback.
- [ ] A data-minimization test shows the provider receives only the selected requirement and authorized relevant context, not the full knowledge pack or document repository.

## Before production

### Production blockers

- [ ] Confirm whether the system remains an engineering aid. If it becomes an official QMS/regulated record system, stop release until electronic signatures, immutable audit trails, validation, change control, and required record retention are separately specified and accepted.
- [ ] Confirm tenant model, knowledge ownership/visibility, deployment region, permitted data classes, cross-border rules, deletion/retention policy, and legal/compliance owner approval.
- [ ] Confirm the OIDC issuer, audience, signing algorithms, claims, group-to-role/project mapping, joiner/mover/leaver process, and emergency access process.
- [ ] Confirm approved LLM/embedding/OCR providers and models, regional endpoints, contract terms, budgets/quotas, and outage behavior.
- [ ] Confirm production platform, secret manager/KMS, network egress policy, monitoring/on-call ownership, incident-response process, availability target, RPO, and RTO.

### Build checklist

- [ ] Use OIDC Authorization Code with PKCE. Validate JWT signature, issuer, audience, expiry, not-before, and allowed algorithms. Default access-token lifetime to 15 minutes; use a `Secure`, `HttpOnly`, `SameSite` refresh/session cookie where applicable.
- [ ] Encrypt service traffic in transit and persistent data/backups at rest. Rotate secrets at least every 90 days and immediately after suspected exposure.
- [ ] Default-deny network egress and allow only the IdP, approved AI providers, object storage, and required internal services.
- [ ] Make audit events append-only and separately authorized. Cover authentication, membership/role changes, upload/view/download, create/edit/review/reject, AI generation, export, deletion, configuration changes, and failed authorization.
- [ ] Apply per-tenant upload, queue-concurrency, request, token, and cost quotas. Alert on repeated access denial, validator failures, provider cost/error spikes, stuck jobs, DLQ growth, and backup failures.
- [ ] Run daily encrypted backups of PostgreSQL and object storage; include vector reconstruction or backup. Redis is not backed up as business truth. Default targets are RPO 24 hours and RTO 4 hours.
- [ ] Generate an SBOM and scan dependencies, source, secrets, and container images. Production release permits zero unresolved Critical vulnerabilities; exceptions require an owner, expiry, and compensating control.

### Release gate

- [ ] The full authorization matrix passes against the production-like OIDC configuration and shared database/object/vector stores.
- [ ] A restore exercise recovers a consistent project, documents, embeddings/reconstruction inputs, AI lineage, and audit records within the approved RPO/RTO.
- [ ] A queue outage and provider outage exercise proves bounded retries, circuit breaking, no duplicate billing/assets, no silent provider fallback, and operator-visible recovery.
- [ ] Security scans show no committed secrets or unresolved Critical vulnerability, and the deployed artifact matches the reviewed SBOM/image digest.
- [ ] Incident response, data deletion, key rotation, provider disablement, and tenant access-revocation runbooks have named owners and have been exercised once.
